# 教学与构建规范 v1.0

## 1. 参考机制

课程采用一种从空白逐步构建的教学方式。

```text
看见对象
→ 建立最小版本
→ 运行
→ 观察
→ 解释
→ 暴露问题
→ 只增加一层复杂度
→ 再运行
```

吸引力来自理解正在发生。幽默可以自然出现，不承担教学任务。

## 2. 课程语言

讲师表达保持：

- 平静；
- 具体；
- 准确；
- 技术诚实。

优先说：

> 这一列缺了，任务不能继续。

> 当前输出只说明检查通过，不代表工作已经验收。

> 这里使用模型，因为原始文本存在多种解释。

> 这个数值由负责人确认，系统不替他决定。

避免：

- 宏大趋势开场；
- 咨询报告式排比；
- 网络梗和强行锐评；
- 每段都制造反转；
- 用抽象概念替代动作；
- 用“运行成功”暗示“结果可信”。

## 3. 三轨课程产品

### Main Lesson｜工程理解轨

时长建议：20–30 分钟。

必须出现：

- 今天完成什么；
- 第一次可见结果；
- 一个错误或边界；
- 一次系统修改；
- 一份学员产出。

### Build Lab｜FDE 构建轨

时长建议：45–90 分钟。

完整展示：

- 创建文件；
- 编写和修改代码；
- 执行命令；
- 查看日志；
- 制造错误；
- 增加测试；
- 整理资产。

### Engineering Notes｜工程说明

保存：

- 完整代码；
- 文件结构；
- 数据契约；
- 状态定义；
- 适用范围；
- 已知问题；
- 扩展练习；
- 评审记录。

## 4. 每集标准循环

1. 屏幕出现一个具体文件、表格、日志或请求；
2. 讲师说清今天的一个小目标；
3. 手工或最小代码先跑通一条路径；
4. 检查结果和预期是否一致；
5. 主动引入一个失败；
6. 定位失败发生在哪里；
7. 增加一项规则、状态或人工门禁；
8. 再次运行；
9. 最后给概念命名；
10. 学员迁移到自己的工作。

## 5. 概念进入顺序

概念只有在学员经历对应问题以后才出现。

| 经历的问题 | 随后命名的概念 |
|---|---|
| 请求缺少执行信息 | 输入契约、澄清 |
| 任务无法判断当前阶段 | 状态、状态机 |
| 系统不知道怎样调用程序 | Tool Contract |
| 模型不能直接批准结果 | Human-in-the-loop |
| 对象和关系经常混乱 | Ontology |
| 修改后不知道是否退化 | Eval、回归测试 |
| 无法回看发生过什么 | Trace、Evidence |
| 方法超出适用范围 | Method Applicability Domain |
| 成果无法被别人接手 | Agent Asset Package |

## 6. 每次只增加一层复杂度

以下做法不通过评审：

- 第一集同时加入模型、RAG、多 Agent、UI、数据库和权限；
- 为了显得完整，一次展示最终架构；
- 先讲十个术语，再开始操作；
- 把错误隐藏在剪辑外；
- 只展示正常样例。

复杂度必须由一个可观察问题带入。

## 7. 错误必须留在课程里

每个模块至少保留一条失败路径，并回答：

- 我们原来预计什么；
- 实际发生了什么；
- 问题属于输入、模型、程序、工具、状态、方法还是责任；
- 为什么不能只修改 Prompt；
- 修改后用什么测试证明问题被控制。

## 8. 真人镜头与屏幕内容

仓库覆盖除真人拍摄外的全部内容。

逐字稿中使用统一占位：

```text
[真人镜头｜画面说明｜建议时长]
```

录制完成前，课程仍应可以仅靠：

- 屏幕录制；
- 旁白；
- 字幕；
- SVG 动画；
- 互动页面；
- 终端与文件演示；

完整理解。

真人镜头承担：

- 开场建立关系；
- 关键判断；
- 个人经验；
- 模块收束。

真人镜头不承担必须依靠画面才能理解的技术步骤。

## 9. 视觉规范

减少：

- 发光大脑；
- 机器人头像；
- 装饰性六边形；
- 没有数据含义的科技线条；
- 一页十个概念卡片。

增加：

- 文件与字段；
- 任务状态；
- 输入输出对比；
- 修改前后差异；
- 失败记录；
- 终端输出；
- 一步步生长的结构图；
- 可编辑 SVG。

视觉只做三件事：

1. 显示当前对象；
2. 显示发生了什么变化；
3. 显示我们怎样知道它对或错。

## 10. 逐字稿验收

| 检查项 | 过线标准 |
|---|---|
| 前 2 分钟 | 已出现具体对象与目标 |
| 前 8 分钟 | 已获得第一份可见结果 |
| 实际操作 | 至少一次真实运行 |
| 失败路径 | 至少一个问题被保留 |
| 修改 | 系统因问题发生明确变化 |
| 概念顺序 | 先经历，后命名 |
| 语言 | 具体名词与动作多于抽象判断 |
| 技术诚实 | 未验证内容有明确边界 |
| 学员产出 | 可运行、检查或评审 |
| 结尾 | 回到本集构建结果，不做宏大升华 |

## 11. 模块完成定义

一个模块只有同时具备以下内容才算完成：

- 模块设计卡；
- 完整讲师稿；
- 屏幕操作清单；
- 分镜与真人占位；
- 可运行实验；
- 正常与失败样例；
- 自动测试；
- 学员作业；
- Rubric；
- 参考答案；
- 字幕草稿；
- 可编辑视觉资产；
- 公开安全检查结果。
