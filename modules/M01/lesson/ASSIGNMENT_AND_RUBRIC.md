# M01 学员作业与评分

## 作业名称

《我的第一个任务准备闭环》

## 目标

选择一句日常工作请求，把它变成一张可确认的任务卡，并证明系统在关键信息缺失时会停下。

## 安全要求

提交内容必须为：

- 完全虚构；或
- 保留工作结构、彻底替换所有实际信息的安全样例。

不得包含：

- 真实项目名；
- 真实人员；
- 内部文件和截图；
- 专业参数和阈值；
- 内部工具名、目录和接口；
- 任何可反推业务能力的细节。

## 建议选题

适合：

- 整理报名信息；
- 汇总公开反馈；
- 准备一次虚构周会；
- 制作活动物料清单；
- 检查一组公开文档的元数据；
- 整理个人学习记录。

不适合公开提交：

- 专业仿真；
- 真实会议纪要；
- 内部质量问题；
- 客户、供应商或型号数据；
- 涉及个人隐私的工作记录。

## 提交目录

```text
m01_<task_name>/
```

## README 必答问题

1. 这条请求在什么情况下出现？
2. 原文明确提供了哪些信息？
3. 哪些字段缺失时不能开始？
4. 哪些值由人工确认？
5. 系统怎样区分原文、默认值和人工确认？
6. `READY` 在你的案例中准确表示什么？
7. `READY` 之后仍然有哪些工作没有发生？
8. 你主动测试了哪一种失败？
9. 另一名同学怎样复现？
10. 这份样例为什么可以公开？

## 强制实验

### 实验 A｜无人工确认

运行后必须：

- 状态为 `NEEDS_CLARIFICATION`；
- 生成澄清问题；
- 不把猜测写成确认事实；
- 运行记录说明停止原因。

### 实验 B｜加入人工确认

运行后必须：

- 状态为 `READY`；
- 缺失字段为空；
- `confirmed_by` 存在；
- 人工字段带来源；
- `READY` 定义清楚。

### 实验 C｜错误确认文件

主动制造一个错误：

- 没有 `confirmed_by`；
- 日期范围只有 start；
- 输出为空数组；
- 验收条件为空；
- JSON 格式损坏。

系统应拒绝确认文件，并给出清楚原因。

## 评分 Rubric

总分 10 分。

### 1. 安全与来源｜0–2

**2 分**：样例完全公开安全，来源和边界说明清楚。  
**1 分**：完成基本替换，但仍有不必要的真实结构或模糊来源。  
**0 分**：包含不应公开的信息；停止评审并删除材料。

### 2. 任务边界｜0–2

**2 分**：必填字段、停止条件和 `READY` 含义明确。  
**1 分**：字段基本完整，状态含义仍偏大。  
**0 分**：系统仍会在关键字段缺失时继续。

### 3. 人工确认｜0–2

**2 分**：原文、系统候选和人工确认清楚区分。  
**1 分**：有人工环节，但确认来源或字段范围不清。  
**0 分**：系统把猜测直接写成事实。

### 4. 可复现与测试｜0–2

**2 分**：同学可按 README 运行；正常、停止和错误输入均有测试。  
**1 分**：主路径可运行，失败测试不足。  
**0 分**：无法复现或只提供截图。

### 5. 证据与解释｜0–2

**2 分**：原始请求、问题、确认、状态和原因均可回看。  
**1 分**：保留部分输出，缺少形成过程。  
**0 分**：只有最终任务卡。

## 晋级标准

- 7–10 分：进入 M02；
- 5–6 分：缩小任务或补齐失败路径；
- 0–4 分：重新选择一个更小、更安全的任务。

## 同行评审问题

评审人只问：

1. 哪个字段最容易被系统偷偷猜掉？
2. 缺少哪个信息时必须停？
3. `READY` 有哪些证据？
4. 谁承担确认责任？
5. 作者不在时，另一名同学能不能复现？
6. 这份材料能否安全放到公开仓库？

## 参考答案边界

参考实现位于：

```text
modules/M01/lab/
```

学员可以复用数据结构和测试方法，不应只改几个文本值后提交。至少需要修改：

- 一条原始请求；
- 必填字段或问题映射；
- 一项确认规则；
- 一条失败测试；
- README 中的边界解释。
